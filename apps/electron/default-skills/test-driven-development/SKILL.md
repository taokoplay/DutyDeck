# 测试驱动开发

让测试证明目标行为和修复效果，再用最小实现满足要求。测试方法在本 Skill 维护；`writing-plans` 负责拆解任务，`executing-plans` 负责推进和交付，小任务可直接使用本 Skill。

## 先确认适用范围

- 新功能、行为变更、缺陷修复：先运行针对目标行为的失败测试，再修改实现。
- 保持行为不变的重构：先运行现有测试；缺少覆盖时补充能锁定现有行为的测试并确认通过，再重构。不为制造红灯而故意破坏正常代码。
- 文档、纯样式、一次性原型：按风险选择格式检查、构建或真实交互检查，不为了套流程新增测试设施；支付、权限、持久化等逻辑不能仅因位于原型中就免于验证。
- 用户明确要求其他验证方式时遵循其范围，说明实际证据与缺口，不把未执行的 TDD 描述为已完成。

## 开始前

1. 读取当前任务、已授权项目规则、相关业务链路和工作区差异，分清用户已有代码与本轮改动。无需为一个小修复额外创建计划、worktree 或子 Agent。
2. 从目标项目的脚本、锁文件、CI 和现有测试确定运行命令与环境。沿用该项目的测试框架和包管理器，不把 DutyDeck 自身的 Bun 约定强加给 Python、Go 或其他项目，也不默认执行 `npm test`。
3. 用可观察行为定义验收，包含正常路径和主要边界；BDD 的 Given / When / Then 可用于表达。评估关联模块与性能影响，选择能证明该行为的最小测试层级，不要求每个内部方法各写一个测试。

## 新增或修复行为：红 → 绿 → 整理

### 红：先证明问题

- 写一个针对目标行为的测试，并在修改实现前实际运行。阅读断言、退出码和失败原因，确认失败源于目标行为缺失或错误。
- 例如修复“空白名称仍可提交”：先验证全空格输入被拒绝，观察当前代码仍接受而失败；同时保留正常名称可提交的用例。不要只检查某个 mock 被调用。
- 依赖未安装、命令写错、权限不足、网络故障或测试代码拼写错误不算有效红灯。先做已授权、可逆的环境诊断和修复，再重跑；不要引入未获授权的新依赖或靠绕过权限继续。
- 测试首次通过时，核对场景、断言与执行范围，确认问题是否已经修好。不得虚构先前失败，或降低正确断言来制造红灯。

### 绿：最小实现

- 修改直接导致目标行为的代码，运行同一测试并确认通过，再运行相关回归；失败时分析真实原因，不通过删除断言、跳过失败用例或放宽预期制造通过。
- 测试公共行为和真实协作边界；仅在隔离外部服务、不可控时间或昂贵副作用确有必要时使用 mock，并核对替身契约。不要为测试给生产代码增加无业务用途的接口。

### 整理：保持证据有效

- 在测试通过后做必要的命名、重复逻辑或结构整理，随后重跑受影响测试；不顺带扩大功能范围。
- 按项目规则补充类型检查、lint、构建或集成检查。UI、Electron、文件权限与平台差异问题需要相应的真实运行验证；单元测试通过不能替代目标平台或用户流程验收。
- 已通过的检查不无故反复运行全量套件；仅在新增改动、失败或未解决风险要求时扩大验证范围。

## 已有代码与验证受限

- 用户已经写好修复、工作区存在未提交内容，或接手时实现已先于测试：保留已有代码，补回归并如实标记“补充验证”。不要为了遵守顺序删除实现、重置 Git 或覆盖他人改动。
- 若需证明测试能捕获原问题，可在安全的隔离副本中对比修复前后；不要在共享工作区回滚用户代码。无法取得修复前证据时明确说明，不能声称已完成红绿闭环。
- 缺少测试框架时先检查项目已有的可执行检查；测试设施升级需要另行评估，不为小改动擅自安装新框架。无法运行的部分记录命令、阻塞原因、已完成的替代验证与仍未覆盖的行为，继续可独立完成的已授权工作。

## 交付

报告改动解决的行为、实际运行的验证及结果、影响范围与未验证事项。实现完成、测试通过、真实环境验收和发布完成分别陈述；提交、推送、发布沿用用户授权，不由本 Skill 自动授予。

本 Skill 是按需读取的方法指引，不是宿主强制测试门禁；没有工具结果时不能宣称测试已经运行。
